### Dynamic Cell Content (generated by `tubes.js`)

Each `#load{i}{j}` cell is populated with one of:

| Tube State (`used`) | Cell Content (matching ordnance) | Cell Content (other ordnance) |
|---------------------|----------------------------------|-------------------------------|
| 0 (empty) | `<div class="load">LOAD</div>` | `<div class="load">LOAD</div>` |
| 1 (loaded/ready) | `<div class="fire">FIRE</div>` | `<div class="switch">LOAD</div>` |
| 2 (loading) | `<div class="loading">WAIT</div>` | `<div class="wait">WAIT</div>` |
| 3 (unloading) | `<div class="unloading">WAIT</div>` | `<div class="wait">WAIT</div>` |

When stores for a type are 0, `<div class="empty">EMPTY</div>` replaces LOAD/FIRE.

Loading/unloading cells also get a `background-image: linear-gradient(...)` style showing progress.

## Required Behaviors

| # | Behavior | Source |
|---|----------|--------|
| 1 | `initTubes(shipType)`: shows/hides tube rows (`#tube1`-`#tube6`) based on ship's tube count from `model.vesselData`; sets `#maxStores0`-`#maxStores3` | `tubes.js:7-37` |
| 2 | `updateTubes(data)`: on weapons update, refreshes `#currentStores0`-`#currentStores3` from `storesHoming/Nukes/Mines/EMPs` | `tubes.js:40-54` |
| 3 | For each tube 1-6: reads `tubeUsed{i}` and `tubeContents{i}` from `model.weapons`, sets cell innerHTML based on state matrix (LOAD/FIRE/WAIT/EMPTY) | `tubes.js:61-149` |
| 4 | Loading progress gradient: `linear-gradient(to left, #666 {pct}, #363 {pct})` for loading (state 2) | `tubes.js:138-139` |
| 5 | Unloading progress gradient: `linear-gradient(to right, #666 {pct}, #336 {pct})` for unloading (state 3) | `tubes.js:141-142` |
| 6 | Click on `#load{i}{j}`: calls `tubeAction(tube, ordnance)` which fires/loads/unloads based on current tube state | `tubes.js:155-194` |
| 7 | Tube loaded + same ordnance clicked → XHR GET `./fire-tube/{tube}` | `tubes.js:167-170` |
| 8 | Tube loaded + different ordnance clicked → XHR GET `./unload-tube/{tube}`, queues `pendingAutoLoad[tube] = ordnance` | `tubes.js:171-176` |
| 9 | Tube empty + ordnance clicked → XHR GET `./load-tube/{tube}/{ordnance}` | `tubes.js:177-181` |
| 10 | When tube finishes unloading (state returns to 0), auto-loads pending ordnance if `pendingAutoLoad[tube]` is set | `tubes.js:85-90` |
| 11 | `model.on('ownShipInit', initTubes, 1000)` — but `.on()` with 3rd arg may be a bug (see below) | `tubes.js:201` |
| 12 | `iface.on('weaponsUpdate', updateTubes)` — main update hook | `tubes.js:203` |
| 13 | `model.on('loaded', ...)` — calls `updateTubes(model.weapons)` on initial load | `tubes.js:205-207` |
| 14 | Red alert toggles `body.red-alert` class via `redalert.js` | `redalert.js:4-16` |
| 15 | Connection status overlay via `connectionlost.js` | `connectionlost.js:81-113` |

## Update Cadence

No `setInterval` or `requestAnimationFrame` loops. All updates are event-driven:
- `iface.on('weaponsUpdate')` triggers `updateTubes()`
- `model.on('ownShipInit')` triggers `initTubes()`
- `model.on('loaded')` triggers initial `updateTubes()`

## Known Legacy Bugs

| # | Bug | File:Line | Details |
|---|-----|-----------|---------|
| 1 | **`model.on('ownShipInit', initTubes, 1000)` — third argument** | `tubes.js:201` | EventEmitter `.on()` typically takes `(event, callback)`. The `1000` third argument is likely a leftover from a `setTimeout` refactor (commented-out code on lines 198-200 shows a `setTimeout(initTubes, 1000)` pattern). Depending on the EventEmitter implementation, the 1000 is silently ignored or causes unexpected behavior. |
| 2 | **`model.weapons.stores0` etc. aliased but never declared** | `tubes.js:56-59` | Lines 56-59 create aliases `model.weapons.stores0 = model.weapons.storesHoming` etc. These aliases are set every time `updateTubes` is called, which works, but it's a fragile pattern — the aliases are read in `updateTubes` on line 112/118 within the same function call, creating a dependency on assignment ordering. |
| 3 | **`pendingAutoLoad[i] = undefined` instead of `delete`** | `tubes.js:89` | Setting to `undefined` means `pendingAutoLoad[i] !== undefined` (line 85) would still be `false`, so it works, but the key persists in the object. Minor memory/clarity issue. |
| 4 | **Re-declaration of `var oReq` inside `tubeAction()`** | `tubes.js:179` | `var oReq` is declared on line 165 and again on line 179 within the same function scope. Due to hoisting this is harmless but confusing. |
